# 실험·평가·보고서 기록 원칙

## 기존 로컬 자산

팀장이 로컬에서 TF-IDF, 형태소 검색, E5 결합, BGE 재순위화, KURE/Qwen 후보 재평가를 진행했다. [2026-10-20 진행 현황](PROGRESS.md)과 소형 결과 스냅샷은 이 저장소에 공유했다. 연구 코드·전체 실행 로그·모델/인덱스는 아직 반입하지 않았다. 반입 전 원본 파일의 경로와 Git 이력을 확인하고 충돌 없이 가져온다.

연구 수준의 복잡한 모델을 학기말 C 과제의 필수 구현 범위로 자동 편입하지 않는다. 비교할 때 모델·데이터·연산 환경을 동일하게 맞춘다.

## 분리할 두 종류의 실험

1. **검색 품질:** 사람이 자연어로 쓴 질의에 대해 맞는 표현을 잘 찾는가?
   - Hit@1/5/10/100, nDCG@10 등.
   - 표제어 표기 정규화(`어슴푸레-하다` ↔ `어슴푸레하다`) 또는 sense ID를 일관되게 사용.
   - 다의어, 동형 표제어, 동일 뜻풀이 중복을 처리.
   - 4문항만으로 최적 모델이라 주장하지 않는다.
   - 수동 후보 판정표와 독립 평가 질의를 별도로 유지.
2. **시스템 성능:** C 구현/인덱스 최적화로 얼마만큼 빨라졌는가?
   - 최초 로드 시간, 단일/반복 질의 지연(p50/p95), peak memory, 인덱스 크기.
   - 전수 검색 vs 인덱스, `qsort` vs top-k heap, 알고리즘을 고정한 구현 비교.
   - 동일한 기계·스레드·컴파일러 옵션·데이터 크기에서 비교한다.

## 실험 하나당 저장할 것

```text
experiment_id
date
commit_sha
dataset_version / record_count / embedding_model
method / parameters
queries_version / relevance_labels_version
compiler_and_flags / host_cpu / threads
search_latency_ms / init_latency_ms / memory_mb
Hit@K / nDCG@10
reproduction_command
notes / limitations
```

큰 파일(`.npy`, `.onnx`, 원본 JSON, 전체 벡터, 대형 실행 로그)은 기본적으로 추적하지 않는다. 커밋 가능한 크기의 `experiments/results.csv`, `experiments/notes.md`, 설정/요약 보고서 등만 버전 관리한다.

## 정답 판정

- 3: 질의를 정확히 표현, 2: 실용적인 대체어, 1: 다소 관련, 0: 무관.
- 모델이 제안했다는 이유만으로 적합하다고 간주하지 않는다.
- 여러 검색기의 상위 결과를 섞어 사람이 가림 판정할 수 있게 한다.
- 평가용 질의/후보를 학습이나 파라미터 튜닝에 재사용하면 별도 검증셋을 마련한다.

## 결과 보고서 구조

```text
1. 문제 정의와 데이터
2. 방법/자료구조
3. 실험 설계와 평가 지표
4. 검색 품질 비교
5. 실행 시간·메모리·인덱스 크기
6. 실패 사례·한계
7. 결론 및 다음 최적화
```

**원칙:** 구현 완료한 것과 앞으로 시도할 것을 문서에서 구분하고, 수치가 있는 결과는 반드시 재현 가능한 실험에 연결한다.
