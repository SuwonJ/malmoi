# A 작업 순서: 공통 데이터 형식·벡터 로더·로컬 실험 반입

담당: 장수원 · [작업 이슈 #1](https://github.com/SuwonJ/malmoi/issues/1)

목표는 B·C·D가 **같은 소형 데이터와 공통 API로 각자 개발을 시작하게 하는 것**이다. 아래 순서로 진행한다. 데이터 형식과 API는 기존 C 코드 확인 및 팀 합의 전까지 제안이며, 이 문서 추가만으로 구현 완료나 계약 확정을 뜻하지 않는다.

## 0. 이미 끝난 것 확인

- [x] Python 실험 코드·테스트·결과 기록을 `research/`로 반입했다.
- [x] 원래 로컬 작업 트리를 보존하고 `research/IMPORT.json`에 출처·소스 해시를 기록했다.
- [x] `make setup`, `make test`, `make smoke` 및 GitHub CI가 통과했다.

현재 예제는 **직접 작성한 뜻풀이 12개**다. 1,000개 C 개발용 데이터, C 벡터 로더, C 모듈 빌드는 아직 없다. Python 연구를 다시 반입하거나 기존 모델 실험을 전부 재실행할 필요는 없다.

## 1. 기존 C 코드 확인 — 먼저 할 일

- [ ] 기존 `vecdb.c/.h`, `hash.h`, `tokenizer.h`, `Makefile`, 데이터 생성기를 찾아 위치와 Git 상태를 기록한다.
- [ ] 기존 파일을 커밋 또는 별도 백업한 뒤 [인터페이스 초안](INTERFACES.md)과 함수·구조체·파일 형식을 비교한다.
- [ ] 유지할 함수, 수정할 함수, 호출부를 함께 바꿔야 하는 함수를 목록으로 만든다. 기존 코드가 없으면 그 사실을 기록한다.
- [ ] 팀원의 개발 환경(OS·컴파일러·C 표준)과 기존 함수 사용 여부를 확인한다. 기본 목표는 Linux/macOS/Windows에서 C11 코어를 빌드하는 것이다.

**산출물:** 기존 코드 위치·백업 위치·호환성 차이표. 기존 API를 확인하기 전 공용 헤더를 새로 덮어쓰지 않는다.

## 2. 공통 ID·텍스트·벡터 규칙 합의

- [ ] **word ID와 sense ID를 분리**한다. 뜻풀이 레코드는 word ID를 참조하고 원본 `target_code`도 별도 보존한다. 배열 행 번호를 원본 사전 ID로 간주하지 않는다.
- [ ] 원문 표제어와 검색 키를 분리한다. Python 연구처럼 검색 키는 NFC 정규화 후 `-`·`^`를 제거하되 원문은 출력용으로 보존한다. 같은 검색 키라는 이유로 동음이의어의 ID를 합치지 않는다. 원본에서 어휘 단위를 구분할 근거가 없으면 그 한계를 기록한다.
- [ ] C가 Python과 같은 검색 키를 사용하도록 **전처리에서 키를 생성해 저장**한다. C에서 UTF-8 바이트를 한글 글자처럼 자르지 않는다. 기존 `vecdb_find_word`처럼 단일 ID를 반환하는 API의 동음이의어 처리 정책도 B와 정한다.
- [ ] 내부 ID는 `uint32_t`, 개수·메모리 계산은 `size_t`를 사용한다는 안을 검토한다. ID의 유효 범위·실패 값·데이터 재생성 시 안정성을 문서화한다. 재생성으로 ID가 바뀌면 데이터셋 버전/매핑도 바꾼다.
- [ ] 벡터 차원은 파일에서 읽는다. 특정 차원을 C 코드에 고정하지 않는다. 유사어·게임용 단어 벡터와 역사전용 뜻풀이 벡터를 별도 공간으로 취급한다.
- [ ] 각 공간에 `model_id/revision`, 차원, dtype, 풀링, 문서/질의 지시문, 정규화 정책을 기록한다. **차원이 같아도 모델·풀링·질의 방식이 다르면 호환 벡터가 아니다.** E5/KURE/Qwen과 단어 평균 벡터를 섞어 비교하지 않는다.
- [ ] dense 벡터는 float32를 기본안으로 두고, 정규화 여부·0벡터 처리·NaN/Inf 거부 정책을 정한다. TF-IDF sparse 인덱스는 별도 형식으로 두며 dense 배열로 억지 변환하지 않는다.

**산출물:** 갱신한 `docs/INTERFACES.md`와 새 `docs/DATA_FORMAT.md`. A·B·C·D가 읽고 같은 ID·모델 공간을 이해하면 완료다.

## 3. 파일 규격과 공용 헤더를 함께 고정

- [ ] `tools/prepare.py`가 쓸 바이트 순서와 `src/vecdb.c`가 읽을 바이트 순서를 하나의 명세에 적는다.
- [ ] magic, 형식 버전, 헤더 길이, 레코드 수, 차원, 문자열/벡터 구간의 길이·오프셋, 모델·데이터 식별자를 명시한다. 정수는 고정 폭 little-endian, 실수는 IEEE 754 float32를 기본안으로 검토한다.
- [ ] Python `struct`는 명시적 little-endian 형식을 사용하고, C는 필드를 읽어 변환한다. C `struct` 전체를 그대로 저장하지 않는다. 패딩·포인터·호스트 `size_t`가 파일에 들어가지 않게 한다.
- [ ] UTF-8 문자열 길이는 바이트 단위로 정의한다. 길이에 NUL을 포함하는지 명시하고, C API가 반환하는 문자열의 NUL 종료를 보장한다. 잘린 문자열·잘못된 UTF-8 입력의 처리도 정한다.
- [ ] 기존 초안의 `vecdb_open`/`vecdb_close`를 출발점으로 개수·차원·표제어·뜻풀이·벡터 조회 API를 추가한다. 내부 구조체는 opaque하게 유지해 팀 코드가 파일 배치를 직접 참조하지 않게 한다.
- [ ] 반환 문자열/벡터는 읽기 전용이며 DB를 닫기 전까지만 유효하다는 수명 규칙을 적는다. `out` 초기화, 빈 결과, 미등록 ID, 파일 오류를 구분하는 상태 코드를 정한다.

**산출물:** `include/vecdb.h`, `docs/DATA_FORMAT.md`, 변경한 `docs/INTERFACES.md`. 정확한 함수명·인자·에러 정책을 먼저 공유하면 B·C·D는 로더를 기다리지 않고 같은 헤더의 mock으로 작업할 수 있다.

## 4. Python 전처리기와 작은 fixture 만들기

- [ ] `tools/prepare.py`에서 `research`의 기존 JSONL 필드(`id`, `word`, `definition`, `word_type`, `pos`, `sense_type`)를 입력으로 받을 수 있게 한다. 연구용 스키마를 깨지 않는다.
- [ ] 단어/뜻풀이 매핑, 검색 키, 벡터와 메타데이터를 생성한다. 벡터가 없는 단어의 제외·오류 정책과 최종 개수를 기록한다.
- [ ] 먼저 직접 작성한 수십 개 레코드와 작은 고정 벡터로 C/Python 상호 확인용 fixture를 만든다. 데이터에 동음이의어·다의어·구분 기호 표제어·없는 단어·0벡터 사례를 포함한다.
- [ ] 같은 seed·입력·설정으로 동일한 출력이 나오게 한다. 샘플의 원본 ID, 선택 조건, 해시와 생성 명령을 기록한다.
- [ ] 다음으로 **word 1,000개 기준**의 개발용 세트를 만든다. 해당 단어들의 sense 수는 별도로 표기한다. 예산에 따라 기준을 바꿀 경우 팀 문서도 함께 고친다.
- [ ] 실제 사전/모델을 쓴 1,000개 세트는 출처·라이선스에 맞는 전달 방법을 정한다. Git에는 직접 작성한 fixture와 생성기·설정·해시를 우선 공유한다. 가짜 벡터에는 `synthetic` 표기를 하고 품질 평가에 쓰지 않는다.

**산출물:** 전처리기, 테스트 fixture, 1,000개 개발용 세트의 생성 설정·전달 위치. C 담당자는 모델 다운로드나 Python 추론 없이 fixture를 읽을 수 있어야 한다.

## 5. C 벡터 로더와 공통 계산 구현

- [ ] `src/vecdb.c`에서 파일 열기·헤더/버전 확인·레코드/문자열/벡터 로딩·조회·해제를 구현한다.
- [ ] 파일 크기와 모든 길이·오프셋·ID 범위를 검사한다. `count * dimension * sizeof(float)` 등의 오버플로와 과도한 할당을 막고, 부분 실패 때도 메모리/파일을 해제한다.
- [ ] 단어→벡터, sense→word/뜻풀이, ID→원문을 왕복 조회한다. B의 문자열 해시 테이블 구현과 중복 소유하지 않도록 경계를 맞춘다.
- [ ] 공통 내적/코사인 함수를 구현한다. 양쪽 벡터가 L2 정규화된 경우만 내적을 코사인으로 사용하고 0벡터 정책을 지킨다.
- [ ] 차원/모델 공간이 맞지 않는 입력을 거부한다. DB를 닫은 뒤 반환 포인터를 사용하지 않도록 예제도 작성한다.

**산출물:** `vecdb.c/.h`와 최소 실행 예제. 유사어 순위는 B, 질의 전처리/역사전은 C, 게임 규칙은 D가 소유한다.

## 6. Python ↔ C 호환성·메모리 검증

- [ ] 같은 fixture에서 두 언어가 읽은 ID·검색 키·원문·차원·벡터 값을 비교한다. float32 오차 허용치는 명시한다.
- [ ] 같은 두 벡터의 내적/코사인이 오차 범위 내에서 일치하는지 확인한다. 동점 순위가 필요하면 점수 내림차순·안정 ID 오름차순 규칙을 공유한다.
- [ ] 빈 DB·없는 ID·잘린 헤더/벡터·잘못된 버전·비정상 크기·잘못된 문자열·NaN/Inf·0벡터를 시험한다.
- [ ] 반복 열기/닫기와 중간 실패 경로를 검사한다. GCC/Clang 경고를 확인하고 지원 환경에서 AddressSanitizer/UndefinedBehaviorSanitizer를 실행한다.
- [ ] Python 테스트를 계속 통과시키고 C 검사도 CI에 추가한다. Windows는 MSVC 또는 MinGW 중 실제 검증한 환경을 명시한다. 코어에 POSIX 전용 함수를 넣을 필요가 있으면 대체 경로를 둔다.

**산출물:** 호환성 테스트, C 메모리 검사 결과, 실제로 검증한 OS·컴파일러·명령.

## 7. 팀원이 받을 개발 묶음 완성

- [ ] 기존 Python용 `make setup/test/smoke`를 유지하면서 C용 `make core-test`·모듈별 빌드 타깃을 추가한다. `CC`·`CFLAGS`를 덮어쓸 수 있게 하고 서버/모델 라이브러리 없이 코어만 빌드되게 한다.
- [ ] **B:** word ID·표제어·단어 벡터 열람 예제와 자기 자신 제외/동음이의어 정책을 전달한다.
- [ ] **C:** sense ID→word ID·뜻풀이 매핑과 역사전용 모델 공간/질의 생성 규칙을 전달한다. C에서 질의 벡터를 만들 수 있는 baseline을 함께 정한다.
- [ ] **D:** B와 같은 단어 벡터 공간, 게임 후보 word ID 목록, 미등록 추측 처리 기준을 전달한다.
- [ ] 새 clone에서 문서에 적힌 명령만으로 fixture 생성·C 로딩·벡터 비교까지 실행해 본다. 다른 팀원 한 명의 환경에서도 확인한다.

**A 완료 기준:** 팀원이 대용량 사전/모델 없이 작은 fixture를 받아 ID 조회·뜻풀이 출력·벡터 비교를 실행할 수 있고, 동일한 헤더로 자기 모듈을 빌드할 수 있다.

## 지금 시작할 순서

오늘은 **① 기존 C 코드 위치/헤더 확인 → ② ID·벡터 공간 규칙 합의 → ③ 공용 헤더와 파일 명세 작성**까지 진행한다. 그다음 작은 fixture로 Python 작성기와 C 로더를 먼저 맞추고 1,000개 데이터로 확대한다. 전체 사전 벡터 재생성·KURE 확장 실험·ANN·웹 서버는 이 공통 기반 뒤에 진행한다.
